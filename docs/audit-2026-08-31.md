## Eje 1 — Código muerto

### [INFO] Import `Any` sin usar
- **Archivo:** `core/middleware.py:1`
- **Evidencia:** `from typing import Any` no se usa en el resto del archivo.
- **Por qué es un problema:** warning cosmético de lint; nada funcional.
- **Fix sugerido:** eliminar el import.

### [LOW] `get_or_create` de Profile duplica la señal `post_save`
- **Archivo:** `core/views.py:441-445`
- **Evidencia:**
  ```python
  profile, _ = Profile.objects.get_or_create(
      user=user, defaults={"must_change_password": True}
  )
  profile.must_change_password = True
  profile.save()
  ```
  Combinado con `core/signals.py:6-9` (auto-creación del Profile en cada `User.save()`), la rama `_` del `get_or_create` siempre es `False`. El `.save()` posterior sobrescribe el valor.
- **Por qué es un problema:** código defensivo redundante que oscurece la intención.
- **Fix sugerido:** `profile = user.profile; profile.must_change_password = True; profile.save()`.

### [MEDIUM] `AuditLog.Action.GRANT_EXPIRED` definido pero nunca emitido
- **Archivos:** `core/models.py:82` (definición) y `core/management/commands/expire_grants.py:9` (UPDATE sin audit-log).
- **Evidencia (expire_grants.py):**
  ```python
  updated = AccessGrant.objects.filter(status="active", end_at__lte=timezone.now()).update(status="expired")
  ```
  `rg GRANT_EXPIRED|grant_expired|Action.GRANT_EXPIRED` muestra que el enum solo se referencia a sí mismo y al historial de migraciones (0004/0005/0007). El comando flipa el estado sin escribir una fila de `AuditLog`.
- **Por qué es un problema:** el audit-log queda incompleto y el enum es peso muerto.
- **Fix sugerido:** emitir `log_action(..., Action.GRANT_EXPIRED, ...)` desde `expire_grants.handle`, o borrar el enum + migraciones.

### [LOW] Templates `resource_create.html` / `resource_delete.html` inalcanzables desde la UI
- **Archivos:** `core/views.py:101` y `core/views.py:194`.
- **Por qué es un problema:** los modales postean directo al endpoint; el GET solo lo ve alguien que adivine la URL.
- **Fix sugerido:** `@require_POST` o eliminar el render GET.

### [INFO] `app.js` carga globalmente pero solo sirve en login
- **Archivos:** `core/templates/core/base.html:98`, `core/static/core/js/app.js:1-56`.
- **Por qué es un problema:** la IIFE ya tiene guardia `if (!card || !form || !btn) return;`, así que no rompe, pero infla el bundle.
- **Fix sugerido:** mover el bloque a `auth.js` incluido solo en plantillas de auth.

### [INFO] Listener `htmx:afterSettle` de nav-active es no-op
- **Archivo:** `core/static/core/js/app.js:59-67`.
- **Por qué es un problema:** la clase `--active` ya viene del server-render; el listener JS es redundante.
- **Fix sugerido:** eliminar el listener.

## Eje 2 — Código huérfano / sin conexión

### [MEDIUM] `ensure_superuser`: permisos del grupo `admin` fuera del `transaction.atomic()`
- **Archivo:** `core/management/commands/ensure_superuser.py:69-105`.
- **Evidencia:**
  ```python
  admin, _ = Group.objects.get_or_create(name="admin")   # fuera de atomic
  for codename in ADMIN_GROUP_PERMISSIONS:                # fuera de atomic
      ...
      admin.permissions.add(perm)                          # fuera de atomic

  try:
      with transaction.atomic():                           # empieza AQUÍ
          user, created = User.objects.get_or_create(username=username)
          ...
  ```
- **Por qué es un problema:** la atomicidad protege la mitad equivocada del flujo. Si la DB cae entre línea 84 y 87 queda el grupo admin sin permisos y el superusuario sin crear.

## Eje 3 — Código duplicado

### [HIGH] Snapshot de Resource repetido 4 veces (bloque de 5 campos)
- **Archivo:** `core/views.py:111-117, 128-134, 159-165, 176-182`.
- **Evidencia (extracto 111-117):**
  ```python
  before = {
      "name": resource.name,
      "resource_type": resource.resource_type,
      "environment": resource.environment,
      "url": resource.url,
      "is_active": resource.is_active,
  }
  ```
  Literal idéntico en las otras tres ubicaciones.
- **Por qué es un problema:** un campo nuevo en `Resource` obliga a tocar 4 sitios; ya hay drift: `resource_data` (159-165) omite `owner` por accidente.
- **Fix sugerido:** extraer `def _resource_snapshot(r): return {...}` y reutilizar en los 4 sitios.

### [HIGH] Snapshot de Grant repetido 2 veces en `grant_revoke` (bloque de 7 campos)
- **Archivo:** `core/views.py:250-258, 261-269`.
- **Evidencia:**
  ```python
  before = {
      "user": grant.user.username,
      "resource": grant.resource.name,
      "access_level": grant.access_level,
      "status": grant.status,
      "start_at": grant.start_at.isoformat(),
      "end_at": grant.end_at.isoformat() if grant.end_at else None,
      "notes": grant.notes,
  }
  ...
  after = { ... idéntico ... }
  ```
- **Por qué es un problema:** burden de mantenimiento; inconsistencias triviales generarían diffs falsos en el audit-log.
- **Fix sugerido:** `def _grant_snapshot(g): return {...}`.

### [HIGH] `user.groups.first().name if user.groups.exists() else None` con divergencia
- **Archivo:** `core/views.py:429, 457` (con guarda) vs `core/views.py:391` (sin guarda).
- **Evidencia (391):**
  ```python
  "role": user.groups.first().name,
  ```
  Crashea con `AttributeError` si el usuario no tiene grupo, a diferencia de 429 y 457.
- **Por qué es un problema:** misma lógica en 3 sitios, una de ellas crash-prone. Near-duplicate divergence clásica.
- **Fix sugerido:** helper `_user_role(user) -> str | None`.

### [MEDIUM] `is_ajax = request.headers.get("X-Requested-With") == "XMLHttpRequest"` repetido 6 veces
- **Archivo:** `core/views.py:74, 107, 200, 369, 422, 191`.
- **Por qué es un problema:** línea idéntica una y otra vez; fácil de olvidar al añadir la sexta vista.
- **Fix sugerido:** helper o decorador `@ajax_required`.

### [MEDIUM] Boilercode `form.is_valid() → save → log_action` repetido en 5 vistas
- **Archivo:** `core/views.py:79-88, 121-135, 205-223, 348-360, 373-393, 432-459`.
- **Por qué es un problema:** `resource_create`, `resource_update`, `grant_create`, `user_create`, `user_update`, `user_toggle_active` ejecutan el mismo esqueleto de 8-12 líneas con variantes menores. Los defectos reales se esconden en las variantes (ver Eje 4 [CRITICAL]).
- **Fix sugerido:** context manager `@log_audit(action)` que envuelva `with transaction.atomic(): obj.save(); AuditLog.objects.create(...)`.

### [MEDIUM] Bootstrap de fixtures de test repetido 3 veces en `conftest.py`
- **Archivo:** `conftest.py:5-17, 30-43, 45-58`.
- **Evidencia:**
  ```python
  user = User.objects.create_user(username="...", password="...")
  user.profile.must_change_password = False
  user.profile.save()
  user.groups.add(group)
  client.login(username="...", password="pass")
  return client
  ```
- **Por qué es un problema:** `viewer_client`, `editor_client`, `admin_client` repiten las 5 líneas de bootstrap; solo cambian los codenames de grupo.
- **Fix sugerido:** factory helper `_make_group_client(name, codenames)`.

### [LOW] `bootstrap_roles` y `ensure_superuser` comparten el lookup de permisos admin
- **Archivos:** `core/management/commands/bootstrap_roles.py:38-44` y `core/management/commands/ensure_superuser.py:72-83`.
- **Por qué es un problema:** el constante `ADMIN_GROUP_PERMISSIONS` ya está compartida, pero el cuerpo del lookup no.
- **Fix sugerido:** extraer `_grant_admin_perms(group)`.

## Eje 4 — Flujos mal formados

### [CRITICAL] `user_create` puede crashear con `AttributeError` al loguear
- **Archivo:** `core/views.py:391`
- **Evidencia:**
  ```python
  "role": user.groups.first().name,
  ```
  Las otras dos sitios (líneas 429 y 457) defienden con `if user.groups.exists() else None`. Esta no.
- **Por qué es un problema:** cualquier adaptador, señal o cambio de form que limpie grupos entre `user.groups.add(...)` (380) y `log_action(...)` (381) lanza 500. Inconsistente con el resto.
- **Fix sugerido:** `"role": user.groups.first().name if user.groups.exists() else None`.

### [HIGH] `user_update` muta user + groups + profile SIN `transaction.atomic()`
- **Archivo:** `core/views.py:432-446`
- **Evidencia:**
  ```python
  if form.is_valid():
      user = form.save(commit=False)
      user.groups.clear()
      user.groups.add(form.cleaned_data["role"])
      password = form.cleaned_data.get("password")
      if password:
          user.set_password(password)
          profile, _ = Profile.objects.get_or_create(
              user=user, defaults={"must_change_password": True}
          )
          profile.must_change_password = True
          profile.save()
      user.save()
  ```
  5 escrituras distintas (groups.clear, groups.add, set_password, profile.save, user.save) sin atomicidad.
- **Por qué es un problema:** una caída de DB entre dos escrituras deja al usuario medio-actualizado (p. ej. password rotado pero grupo viejo todavía pegado).
- **Fix sugerido:** envolver en `with transaction.atomic():`.

### [HIGH] `submitForm` no distingue HTTP 403 (CSRF expirado) de "Error de red"
- **Archivo:** `core/static/core/js/delegated.js` `submitForm`.
- **Por qué es un problema:** Django responde HTML al 403, `r.json()` lanza `SyntaxError` y el catch muestra "Error de red" en vez de "Sesión expirada, recarga la página".
- **Fix sugerido:** detectar `r.status === 403` y mostrar mensaje claro.

### [HIGH] `grant_revoke` sin lock; race con revocación concurrente
- **Archivo:** `core/views.py:248-277`.
- **Evidencia:** lee `grant.status`, muta a `REVOKED`, guarda, sin `select_for_update`.
- **Por qué es un problema:** doble pulsación o dos admins simultáneos duplican el audit-log con `before/after` idénticos.
- **Fix sugerido:** `AccessGrant.objects.select_for_update().get(pk=pk)` antes de la mutación.

### [HIGH] `seed_data` usa contraseñas hardcodeadas y se puede activar en producción
- **Archivo:** `core/management/commands/seed_data.py:16,21,26`.
- **Evidencia:** passwords conocidos para `viewer1`, `editor1`, `admin1`.
- **Por qué es un problema:** si `SEED_DEMO=True` se prende en Render, entran usuarios de password conocida al sistema real sin marca de seed.
- **Fix sugerido:** generar passwords aleatorias y loguearlas, o rechazar ejecutar si `DEBUG=False`.

### [HIGH] `SECRET_KEY` sin fail-fast en settings
- **Archivo:** `accessledger/settings.py:26`.
- **Evidencia:** `SECRET_KEY = os.environ.get("SECRET_KEY")`.
- **Por qué es un problema:** si la env var falta en producción, Django arranca con `None` y las sesiones son falsificables silenciosamente.
- **Fix sugerido:** `if not SECRET_KEY: raise ImproperlyConfigured(...)`.

### [MEDIUM] `ALLOWED_HOSTS` parsea vacío como `[""]`
- **Archivo:** `accessledger/settings.py:30`.
- **Evidencia:** `os.environ.get("ALLOWED_HOSTS", "").split(",")` con default `""` produce `[""]`.
- **Por qué es un problema:** Render sin `ALLOWED_HOSTS` definido rompe el primer deploy con error poco claro.
- **Fix sugerido:** validar no-vacío cuando `DEBUG=False`.

### [MEDIUM] `ForcePasswordChangeMiddleware` bloquea `/admin/login/`
- **Archivo:** `core/middleware.py:5`.
- **Evidencia:** `ALLOWED_PATHS = ["/password/change/", "/login/", "/admin/"]` con comparación `not in` (exacta). `/admin/login/` no está en la lista.
- **Por qué es un problema:** un admin con `must_change_password=True` no puede autenticarse para arreglar el sistema desde la UI admin.
- **Fix sugerido:** `startswith` para `/admin/` y `/password/change/`, o agregar `/admin/login/` explícito.

### [MEDIUM] `expire_grants` actualiza sin audit-log (re-citado del Eje 1)
- **Archivo:** `core/management/commands/expire_grants.py:9`.
- Ver hallazgo MEDIUM del Eje 1.

### [MEDIUM] `ensure_superuser` fail-open cuando faltan env vars
- **Archivo:** `core/management/commands/ensure_superuser.py:57-61`.
- **Evidencia:**
  ```python
  if not username or not password:
      self.stdout.write(self.style.WARNING(
          "[ensure_superuser] SKIP: DJANGO_SUPERUSER_USERNAME/PASSWORD not set"
      ))
      return
  ```
  Docstring dice "fail-closed si presentes", pero ausentes → exit 0 con WARNING.
- **Por qué es un problema:** un Render con env mal configurado deploya app sin admin y nadie se entera.
- **Fix sugerido:** flag `--require-env` para producción, o aserción al startup cuando `DEBUG=False`.

### [LOW] `audit_log` permite a un admin desactivarse a sí mismo
- **Archivos:** `core/views.py:471-486` + `user_toggle_active`.
- **Por qué es un problema:** sin guard `request.user != target_user`, un admin puede desactivarse a sí mismo y bloquear el sistema si es el único admin activo.
- **Fix sugerido:** rechazar self-toggle y mantener invariante "al menos un admin activo".

### [LOW] `password_change.js` requiere variable global `USERNAME` inyectada por template
- **Archivos:** `core/static/core/js/password_change.js:36` y `templates/registration/password_change_form.html:104`.
- **Por qué es un problema:** acoplamiento implícito no documentado.
- **Fix sugerido:** inyectar vía `data-*` o mover la validación al servidor.

### [INFO] `datetime.now()` / `datetime.utcnow()` — verificado limpio
- `USE_TZ=True` y `expire_grants` usa `timezone.now()`. Sin naive datetimes.

## Top 5 acciones recomendadas

1. **Fix CRITICAL `views.py:391`** — agregar `if user.groups.exists() else None`. Una línea, sin riesgo.
2. **Extraer helpers `_resource_snapshot` / `_grant_snapshot` / `_user_role`** — elimina 4 + 2 + 2 duplicaciones y reduce los touch-points de un campo nuevo de 4-5 a 1.
3. **Envolver `user_update` (`views.py:432`) y el seed de permisos de `ensure_superuser` (`ensure_superuser.py:69`) en `transaction.atomic()`** — atomicidad donde más duele.
4. **Implementar el audit-log de `expire_grants` con `GRANT_EXPIRED` o borrar el enum + sus migraciones** — cerrar el único `Action` sin call-site.
5. **Fail-fast en producción sobre `SECRET_KEY`, `ALLOWED_HOSTS` y `DJANGO_SUPERUSER_PASSWORD`** — un Render mal configurado no debería poder deployar una app falsificable.
